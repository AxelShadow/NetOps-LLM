# Промт для AI-агента: миграция чата на Chainlit, админки на FastAPI + Jinja2 + HTMX + Tailwind CSS

Ты — старший fullstack-инженер, отвечающий за безопасную и поэтапную миграцию проекта `NetOps-LLM`.

Твоя задача — перевести пользовательский интерфейс проекта с монолитного `frontend/index.html` на гибридную архитектуру:

1. Чат и визуализация работы LLM-агента — через **Chainlit**.
2. Инвентарь устройств, аудит, настройки, пользователи, история и другие административные разделы — через **FastAPI + Jinja2 + HTMX + Tailwind CSS**.
3. Backend FastAPI остается главным источником бизнес-логики, RBAC, аудита, инструментов и агентского цикла.
4. Chainlit не должен становиться вторым местом, где дублируются инструменты, права доступа или логика вызова LLM.

Работай аккуратно, поэтапно, без резкой перезаписи существующей системы. Старый монолитный интерфейс должен оставаться доступным до завершения миграции и проверки нового решения.

---

## 1. Контекст текущего проекта

Проект `NetOps-LLM` имеет следующую архитектуру:

- `backend/` — FastAPI-приложение.
- `frontend/index.html` — весь текущий интерфейс одним файлом на vanilla JS.
- `nginx/` — reverse proxy, критично `proxy_buffering off` для SSE.
- `docker-compose.yml` — прод-окружение: app + nginx + postgres.
- Авторизация: AD/LDAP + локальная таблица прав.
- Роли: `admin`, `engineer`, `viewer`.
- Чат работает через SSE-стриминг.
- Агентский цикл поддерживает tool-calling до 20 шагов.
- Есть реестр инструментов:
  - VMware;
  - Zabbix;
  - ping;
  - композитные инструменты вроде `get_device_full_health`, `get_infrastructure_health`.
- Есть аудит каждого вызова инструмента.
- Есть инвентарь устройств.
- Есть история диалогов.
- LLM-сервер — LM Studio, скрыт от пользователей, доступен только из app-сервера.

Ключевые файлы, которые нужно изучить перед началом:

```text

docker-compose.yml
.env.example
nginx/nginx.conf
backend/app/main.py
backend/app/config.py
backend/app/db.py
backend/app/models.py
backend/app/api/chat.py
backend/app/api/devices.py
backend/app/agent/tools.py
backend/app/llm/client.py
backend/app/auth/
frontend/index.html
```

Не выдумывай поведение системы. Сначала читай код, затем формируй план, затем меняй код.

## 2. Главная цель миграции

Необходимо получить следующую архитектуру:

```text
Браузер
  |
  |-- /chat        -> Chainlit UI для общения с агентом
  |-- /admin       -> FastAPI + Jinja2 + HTMX + Tailwind CSS
  |-- /api         -> FastAPI JSON API
  |-- /internal    -> внутренние endpoint'ы для auth-check и service-to-service вызовов
  |
  v
Nginx
  |
  |-- FastAPI app
  |-- Chainlit app
```

Chainlit отвечает только за удобный чат-интерфейс и визуализацию шагов агента.

Выполнение инструментов, проверка прав, запись аудита, работа с LLM и инфраструктурными системами остаются в FastAPI.

## 3. Жесткие ограничения

Соблюдай следующие обязательные ограничения:

1. Не переноси выполнение инструментов в Chainlit.
2. Не дублируй агентский цикл в Chainlit, если можно использовать существующий бэкенд.
3. Не ослабляй авторизацию и RBAC.
4. Не открывай LLM-сервер напрямую браузеру.
5. Не используй секреты, ключи, токены и пароли в клиентском коде.
6. Не удаляй старый `frontend/index.html` до финальной фазы.
7. Не ломай существующий SSE-чат до появления рабочей замены.
8. Не включай мок-режим в продакшене по умолчанию.
9. Все изменения должны быть поэтапными и откатываемыми.
10. Каждая фаза должна заканчиваться работоспособным состоянием проекта.
11. Все серверные действия должны проверять права пользователя, а не только прятать кнопки в интерфейсе.
12. Аудит вызовов инструментов должен сохраняться так же, как сейчас, или лучше.
13. Если нужно изменить схему БД, добавь миграцию или отдельный скрипт миграции.
14. Не добавляй тяжелые фронтенд-сборщики для админки, если это не требуется явно.
15. Для админки используй серверный рендеринг через Jinja2 и частичные HTML-фрагменты для HTMX.

- не хранить самостоятельно источник истины по диалогам, если это не требуется для минимального UX.

# Фаза 7. Авторизация Chainlit

## Цель

Пользователь должен попадать в Chainlit только после авторизации в текущей системе.

## Приоритетный вариант

Использовать проверку авторизации через Nginx `auth_request`.

Схема:

```text
Браузер запрашивает /chat
  |
  v
Nginx делает subrequest /internal/auth-check
  |
  v
FastAPI проверяет сессию/токен пользователя
  |
  |-- 204, если доступ разрешен
  |-- 401/403, если доступ запрещен
  |
  v
Nginx проксирует запрос в Chainlit и передает безопасные заголовки
```

## Задачи

1. Добавь внутренний маршрут:

```text
GET /internal/auth-check
```

2. Маршрут должен проверять текущую сессию или токен пользователя.
3. При успехе возвращай 204 и заголовки:

```text
X-User-Id
X-User-Email
X-User-Role
```

4. Добавь проверку, что внутренние заголовки принимаются Chainlit только от доверенного прокси.
5. Добавь заголовок или переменную доверия, например:

```env
NETOPS_PROXY_AUTH_SECRET=change-me
```

6. Chainlit должен читать пользователя из проверенных заголовков только если запрос пришел с корректным секретом прокси.

## Запасной вариант

Если текущая версия Chainlit не позволяет удобно использовать заголовочную авторизацию:

1. Сделай страницу входа внутри Chainlit.
2. Форма должна вызывать существующий FastAPI login API.
3. После успешного входа сохраняй токен или сессию в `cl.user_session`.
4. При каждом запросе к внутреннему API передавай токен пользователя.

## Запрещено

- Позволять анонимный доступ к Chainlit в продакшене.
- Доверять заголовкам пользователя без проверки секрета прокси.
- Хранить пароль пользователя в логах.
- Передавать внутренние секреты в браузер.

## Результат фазы

Добавь тесты или ручной сценарий:

- неавторизованный запрос к `/chat` возвращает 401/редирект на логин;
- авторизованный пользователь видит чат;
- пользователь без роли чата не получает доступ;
- внутри Chainlit доступны `user_id`, `email`, `role`.

# Фаза 8. Интеграция чата

## Цель

Chainlit должен отображать тот же агентский цикл, который уже работает в FastAPI.

## Задачи

1. В `chainlit/client.py` реализуй асинхронный клиент внутреннего API.
2. Клиент должен вызывать:

```text
POST {FASTAPI_INTERNAL_URL}/internal/chat/stream
```

3. Клиент должен передавать:

```text
X-Internal-Service-Token
X-User-Id
```

или пользовательский токен, если выбран запасной вариант авторизации.

4. Клиент должен читать SSE-поток.
5. В `chainlit/adapters.py` преобразуй события бэкенда в объекты Chainlit.

## Отображение событий

Если приходит событие начала сообщения:

- создай `cl.Message`.

Если приходят текстовые части:

- добавляй их в текущее сообщение.

Если приходит вызов инструмента:

- создай `cl.Step` или аналогичный визуальный шаг;
- покажи имя инструмента;
- покажи аргументы, если они безопасны для отображения.

Если приходит результат инструмента:

- обнови шаг;
- покажи статус: успех или ошибка;
- покажи краткий результат;
- при большом результате показывай свернутый вывод или усеченную версию.

Если приходит ошибка:

- покажи пользовательское сообщение об ошибке;
- не показывай стектрейс в продакшене.

Если приходит завершение:

- заверши текущее сообщение;
- сохрани `conversation_id` в сессии.

## Пример целевого пользовательского сценария

```text
Пользователь: Проверь состояние core-switch-01

Chainlit:
  Шаг: Вызов инструмента ping
  Статус: успех
  Вывод: 10.10.10.5 доступен

  Шаг: Вызов инструмента get_device_full_health
  Статус: успех
  Вывод: устройство доступно, загрузка нормальная

Ассистент: Устройство доступно, критических проблем не обнаружено.
```

## Требования к таймаутам

Агентский цикл может работать долго.

Установи разумные таймауты:

- подключение;
- чтение;
- общий запрос.

Добавь понятную ошибку:

```text
Агент слишком долго не отвечает. Повторите запрос или обратитесь к администратору.
```

## Результат фазы

Проверь вручную:

1. Пользователь отправляет сообщение.
2. Появляется ответ.
3. Появляются шаги инструментов.
4. Ошибка инструмента отображается корректно.
5. История текущего диалога сохраняется в бэкенде.
6. Обновление страницы не должно ломать авторизацию.

# Фаза 10. Обновление Nginx

## Цель

Настроить корректную маршрутизацию админки, API и Chainlit.

## Задачи

1. Сохранить существующие маршруты к FastAPI.
2. Добавить маршрут для Chainlit.
3. Настроить `auth_request` для Chainlit.
4. Настроить WebSocket/длинные соединения для Chainlit.
5. Сохранить `proxy_buffering off` там, где используется SSE.
6. Не открывать внутренние маршруты наружу.

## Пример структуры конфигурации

Используй как ориентир, но адаптируй под текущий `nginx/nginx.conf`:

```nginx
upstream app {
    server app:8000;
}

upstream chainlit {
    server chainlit:8001;
}

server {
    listen 80;

    location /api/ {
        proxy_pass http://app;
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 300s;
    }

    location /admin/ {
        proxy_pass http://app;
        proxy_read_timeout 60s;
    }

    location /internal/ {
        internal;
        proxy_pass http://app;
    }

    location /chat {
        auth_request /internal/auth-check;

        auth_request_set $auth_user_id $upstream_http_x_user_id;
        auth_request_set $auth_user_email $upstream_http_x_user_email;
        auth_request_set $auth_user_role $upstream_http_x_user_role;

        proxy_pass http://chainlit;
        proxy_http_version 1.1;

        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";

        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        proxy_set_header X-User-Id $auth_user_id;
        proxy_set_header X-User-Email $auth_user_email;
        proxy_set_header X-User-Role $auth_user_role;
        proxy_set_header X-Proxy-Auth-Secret $netops_proxy_auth_secret;

        proxy_read_timeout 300s;
        proxy_send_timeout 300s;
    }
}
```

Если Chainlit плохо работает на подпути `/chat`, рассмотри вариант отдельного порта или поддомена, но обязательно зафиксируй выбранное решение в документации.

## Результат фазы

Проверь:

- `/admin` работает;
- `/api` работает;
- `/chat` работает только для авторизованных;
- внутренние маршруты недоступны напрямую;
- WebSocket/Chainlit-соединения не обрываются прокси;
- SSE в старом интерфейсе или внутреннем API не буферизуется.
