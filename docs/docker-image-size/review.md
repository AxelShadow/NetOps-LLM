### 1.2. `task-2` (ранбук `docs/docker-image-size/host-disk-runbook.md`) — **REQUEST CHANGES**

Ранбук сильный: порядок «доказательства → бэкап → чистка» соблюдён (раздел 1 ничего не удаляет, 3.0 требует выгруженный дамп **до** деструктивных шагов), у деструктивных команд есть блоки «что теряется / восстановление / нужен ли бэкап», есть явный запрет `docker system prune -a --volumes` и `docker compose down -v`, нет внутренних адресов и секретов, все использованные флаги существуют в Docker CLI 24.0.6 (сверено `--help`-ом установленного клиента и официальными доками, §2.4).

Возврат — по двум находкам, каждая из которых реализует конкретный способ потерять/«спрятать» прод-данные при выполнении ранбука **как написано**:

* **T2-1 (блокирующая).** `host-disk-runbook.md:531` — `docker volume prune --all --force` приведена как исполняемая команда. `--all` удаляет и **именованные** неиспользуемые тома, а `netops-llm_pgdata` — именно именованный том; при опущенном стеке он попадает под удаление. Это прямо противоречит §3.7:569 и §7:887, где та же команда названа запрещённой. Поштучный разбор (`docker volume inspect`) не может «исключить» один том из `prune --all`: у команды нет для этого механизма.
* **T2-2 (блокирующая).** `host-disk-runbook.md:693-697` — `sudo tee /etc/docker/daemon.json` **перезаписывает файл целиком**, оставляя только `data-root`. На прод-хосте активен containerd image store (это следует из пути в ошибке и разбирается в самом ранбуке), а он включается ключом `"features": {"containerd-snapshotter": true}` в этом же файле. Перезапись удалит ключ (и любые другие: зеркала реестра, `log-driver`, `bip` и т. п.); после перезапуска Docker вернётся к overlay2, а по документации «switching storage backends temporarily hides images and containers» — `docker compose up` создаст **новый пустой** том `pgdata`, PostgreSQL инициализирует пустую БД, и это будет выглядеть как потеря прод-данных (реальные данные останутся в скрытом store). Бэкап `daemon.json` в шаге есть, но обнаружение подмены бэкенда в документе не предусмотрено.

Дополнительно (важные/мелкие, не блокируют сами по себе, но должны быть исправлены вместе с блокерами): **T2-3** (`sed` по `root` может молча не сработать), **T2-4** (перезапускается только `docker`, а описано «containerd + docker»), **T2-5** (неточность про `system prune --volumes` и «перевёрнутый акцент» риска), **T2-6** (обозначения `[СОХРАНЕНИЕ]`/`[РИСК: …]` вне легенды), **T2-7** (редирект дампа в `/root` при запуске docker через `sudo`), **T2-8** (`volume prune --filter` поддерживает только `label=…`), **T2-9** (непроверенные числа/утверждения раздела 10).

## 10. Точность формулировок про регистр имени Dockerfile (запрос Lead)

Строки **1055** и **1054** формулируют риск осторожно и, по проверке, корректно:

* Утверждение «Compose при `build: ./backend` без ключа `dockerfile:` ищет по умолчанию `Dockerfile` (с заглавной `D`)» подтверждается Compose Build Specification: при строковой форме `build` «the whole path is used as a Docker context … looking for a canonical `Dockerfile` at the root of the directory», а «Lack of a `Dockerfile` within this folder throws an error» ([compose-spec/build.md](https://github.com/compose-spec/compose-spec/blob/main/build.md)).
* Предсказание дано в условной форме («на регистрозависимой ФС … сборка `app` **упала бы**»), а не как факт о конкретном хосте; документ не приписывает Compose/BuildKit какого-либо «регистронезависимого» разрешения имени и не утверждает, что поведение проверено на демоне. Факты отделены от вывода: констатация (файл в git — нижний регистр, ключа `dockerfile:` нет) → условный вывод → «значит состояние `<каталога-деплоя>` отличается от репозитория» + список проверок на хосте.
* Согласуется с независимым выводом QA: `verification.md:228` («на Linux **может** дать `Cannot locate specified Dockerfile`») и `verification.md:241` (D-2), причём QA дополнительно нашёл тот же риск в `docker-compose.dev.yml:17,41`.
* Незначительное улучшение (не находка): к строке 1055 можно добавить ссылку на спецификацию Compose, как это сделано в §9 для docker-флагов, и упомянуть dev-compose — тогда формулировка станет самодостаточной. Больше документ нигде поведение с регистром не утверждает (проверено `grep`).

## 11. Новые находки после доработки

**R-1 (важное; правка обязательна).** `host-disk-runbook.md:746-753` → в ветке с `jq` результат пишется редиректом (`sudo jq … > /tmp/daemon.json.new`), затем **безусловно** копируется поверх `/etc/docker/daemon.json` (`sudo cp -a /tmp/daemon.json.new /etc/docker/daemon.json`), причём проверки кода возврата нет ни у `jq`, ни у `python3 -m json.tool`, и в блоке нет `set -e`. По семантике POSIX-shell редирект `>` создаёт/усекает файл **до** запуска команды: если `sudo jq` не отработал (например, `jq` виден пользователю, но не в `PATH` у `sudo` из-за `secure_path`; ошибка чтения файла), `/tmp/daemon.json.new` останется пустым; `json.tool` упадёт, но управление дойдёт до `cp` → `/etc/docker/daemon.json` будет заменён **пустым файлом** → Docker стартует без `features.containerd-snapshotter`, backend подменится, и `docker compose up` создаст пустой `pgdata`. Это ровно тот сценарий, который исправлялся в T2-2.
→ Заменить на fail-fast цепочку: `… || { echo "GATE FAIL: jq не отработал — правку НЕ применять, СТОП"; }`, затем `sudo test -s /tmp/daemon.json.new || echo "GATE FAIL: результат пуст — СТОП"` и `python3 -m json.tool /tmp/daemon.json.new && sudo install -m 644 -o root -g root /tmp/daemon.json.new /etc/docker/daemon.json` (копирование — только при успехе всех проверок; шаг 6 `mv` — только после «ГЕЙТ 5»). Локально не воспроизводилось: bash в песочнице не запускается, вывод основан на семантике POSIX-редиректов и на чтении блока (отсутствие `set -e` и проверок кода возврата — факт).

**R-2 (мелкое).** `host-disk-runbook.md:758-762` → «ГЕЙТ 5» сформулирован как текст после `sudo cat`, без машинной проверки; при отсутствии `jq` шаг 5a вообще ничего не изменяет, а следом идёт `mv /var/lib/docker`. Смягчено тем, что «ГЕЙТ 7» (778–780) останавливает сценарий по пустому `docker images`.
→ Добавить явную проверку перед `mv`: `sudo grep -q '"data-root"' /etc/docker/daemon.json || { echo "GATE FAIL: data-root не задан — СТОП"; }`, а в «ГЕЙТ 7» — сверку `docker info --format '{{.DockerRootDir}}'` с ожидаемым новым путём (сейчас он только печатается, строка 773).

**R-3 (мелкое).** `host-disk-runbook.md:753` → `sudo cp -a /tmp/daemon.json.new /etc/docker/daemon.json`: `cp -a` переносит атрибуты **источника**, поэтому владелец/права `/etc/docker/daemon.json` станут такими же, как у файла в `/tmp` (владелец — запускающий пользователь, права по umask 644). Данные это не теряет, но системный конфиг меняет владельца.
→ Использовать `sudo install -m 644 -o root -g root /tmp/daemon.json.new /etc/docker/daemon.json` (или `sudo cp` без `-a` + `sudo chown root:root` и `chmod`).

**R-4 (мелкое).** `host-disk-runbook.md:821-825` → гейт 3a проверяет **текст** `/etc/containerd/config.toml`, а не эффективное значение; если `root` приходит из drop-in (`/etc/containerd/conf.d/*.toml`, о чём документ сам предупреждает в 805–806 и 826–827), `grep -q` по основному файлу проходит ложно, а `mv` (829) уже уведёт данные; ошибка ловится только на «ГЕЙТ 6» (835–839) с откатом.
→ Проверять фактическое значение: `containerd config dump | grep -qE '^[[:space:]]*root[[:space:]]*=[[:space:]]*"<новый-путь>/containerd"'` и при несовпадении — СТОП до `mv`.

**R-5 (мелкое).** `host-disk-runbook.md:996` → пункт 8 чек-листа (`copy-paste`) даёт дамп без варианта для случая, когда `docker` требует `sudo`, тогда как в 3.0 (411–413) этот вариант есть. Оператор, идущий по чек-листу, может получить `Permission denied` (или отказ docker) и не понять, что делать.
→ Добавить в пункт 8 сноску «если docker через sudo — см. вариант в 3.0 (411–413)» либо продублировать `sudo sh -c '…' > "$WORK/…"`.
