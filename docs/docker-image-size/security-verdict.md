## 3. Выводы по шести пунктам проверки

### 3.1. Секреты не попадают в образ — подтверждено

- `chainlit/Dockerfile` больше **не** использует `COPY . .` (единственное место, которое могло затянуть секретный файл из контекста целиком). Копирование — только явными путями.
- `backend/dockerfile` копирует только `requirements.txt` и `app/` — `backend/.env` не копируется (и не попадает в контекст: `backend/.dockerignore:38` `.env`).
- Оба `.dockerignore` содержат `.env` и `.env.*`; **отрицаний нет** (2.5), поэтому секретные файлы не могут быть «возвращены» в контекст.
- `backend/.dockerignore` не ослабляет защиту: `.env`, `.env.*`, `*.key`, `**/*.key`, `*.pem`, `**/*.pem`, `*.crt`, `*.p12`, `.secrets`, `*.db`, `**/*.sqlite*` — на месте.
- Секреты в образ не передаются и через build-time: `ARG` отсутствует, `ENV` содержит только `PYTHONDONTWRITEBYTECODE`, `PYTHONUNBUFFERED`, `CHAINLIT_HOST`, `CHAINLIT_PORT`; в `docker-compose.yml` у сервисов `build:` задан короткой формой без `args:`.

### 3.2. `chainlit/Dockerfile` копирует только явный список — подтверждено

Фактические инструкции копирования (2.6):
`COPY requirements.txt .` → `COPY app.py client.py adapters.py config.py auth.py chainlit.md ./` → `COPY .chainlit ./.chainlit`.
Wildcard-копирования нет; `ADD` нет. Все источники существуют: `chainlit/app.py`, `client.py`, `adapters.py`, `config.py`, `auth.py`, `chainlit.md` и `.chainlit/config.toml` (+ `.chainlit/translations/*.json`) — проверено `glob`. Комментарий в Dockerfile (стр. 19–20) явно фиксирует, что секреты приходят через env compose.

### 3.3. Данные и артефакты исключены

- В рабочих каталогах фактически существуют `backend/.env`, `backend/netops.db`, 26 файлов `backend/app/**/__pycache__/*.pyc`. Все они покрыты правилами `.dockerignore` (`*.db`, `**/*.db`, `__pycache__`, `**/__pycache__`, `*.pyc`, `**/*.pyc`), т.е. в контекст сборки не попадут. Это существенно: `backend/dockerfile` копирует каталог `app/` целиком, и без правила `**/__pycache__` байткод попал бы в образ.
- Отрицаний, ломающих безопасность, нет (2.5).

### 3.4. Прод-инварианты не ослаблены — подтверждено диффом

`task-1` изменил **только** `backend/dockerfile` и `chainlit/Dockerfile` (2.3). Поэтому:
- fail-fast `${VAR:?}` в `docker-compose.yml` не затронут (2.11);
- `NETOPS_ENCRYPTION_KEY`, `NETOPS_INTERNAL_SERVICE_TOKEN`, `CHAINLIT_AUTH_SECRET`, `DB_PASSWORD` — не затронуты; `NETOPS_PROXY_AUTH_SECRET` остаётся с `:-` (осознанно: пусто = header-режим выключен);
- проброс портов не менялся: у `app` и `chainlit` портов наружу нет, публикуется только `web`;
- маршруты nginx `/internal/` и `= /_auth` остались `internal` (2.10).

### 3.5. Сетевая экспозиция — новых нет

- Новых `EXPOSE`/`ports` дифф не добавляет: `EXPOSE 8001` в `chainlit/Dockerfile:21` — **предсуществующая** строка (в диффе идёт контекстом, не добавлением). `EXPOSE` не публикует порт: публикация возможна только через `-p`/`ports`, которых у `chainlit`/`app` нет.
- `ENV CHAINLIT_HOST=0.0.0.0` (`chainlit/Dockerfile:18`) — предсуществующая строка, нужна для доступа nginx к `chainlit:8001` по внутренней сети compose; наружу порт не выходит.
- Базовые образы не заменялись: в обоих Dockerfile строка 1 `FROM python:3.12-slim` — контекстная (не изменена).

### 3.6. Кэш/слои и ротация

- `pip install --no-cache-dir --no-compile` — кэш pip и байткод в слое не остаются (было `--no-cache-dir`, добавлен `--no-compile`); плюс `PYTHONDONTWRITEBYTECODE=1` на рантайме.

- Ротация не затруднена: секреты приходят только через `env_file: .env` (`docker-compose.yml:14`) и `environment` (`:18`, `:27–33`), т.е. пересборка образа при смене секрета не требуется.

## 4. Инцидент при верификации (S-уровень)

**Факт (без значения):** при импорт-пробе исполнителя `devops-image-slim` (task-1) рабочим каталогом был **корень репозитория**; `pydantic-settings` прочитал корневой `.env`, и в текст `ValidationError` попало **значение** одной переменной, которое оказалось в выводе инструмента агента и, следовательно, в транскрипте сессии (и в контексте модели).

**Оценка уровня — `S3` (секрет).** По `.dsh/security/policy.md`: значение из `.env` даёт доступ (пароль БД) и попало в запрещённый канал передачи — «вывод в чат/лог инструмента» (§3). Даже если значение — от локального dev-стенда, политика требует исходить из худшего: файл `.env` — S3-хранилище (§4).

**Механизм (проверен фактически):**
1. `backend/app/config.py:7` — `SettingsConfigDict(env_prefix="NETOPS_", env_file=".env")`; путь `.env` **относительный**, т.е. разрешается от текущего рабочего каталога процесса. Из корня репозитория это корневой `.env`.
2. `pydantic-settings 2.14.2` (`backend/.venv/Lib/site-packages/pydantic_settings/version.py`), значение `extra` по умолчанию — `'forbid'` (`.../pydantic_settings/main.py:564`), и в `backend/app/config.py` оно не переопределено.
3. Незнакомый ключ даёт ошибку `extra_forbidden`, в которой pydantic печатает **`input_value`** — само значение. Воспроизведение на **плейсхолдерах** `S0` (файл-образец, а не `.env`; корневой `.env` не читался) дало:
   `EXC: ValidationError … extra_forbidden, input_value='...', input_type=str`.
4. **Какая переменная:** сканер перечисляет имена переменных корневого `.env` (без значений) — `DB_PASSWORD` и восемь `NETOPS_*`. Все `NETOPS_*` из корневого `.env` соответствуют полям `Settings` и «лишними» не являются; единственный ключ без префикса `NETOPS_` — **`DB_PASSWORD`**. С высокой вероятностью в транскрипт попало значение именно `DB_PASSWORD` (корневой `.env`); **имя требует подтверждения исполнителем** (только имя, без значения).
   Примечание: в `backend/.env` все ключи имеют префикс `NETOPS_` (по данным сканера), поэтому загрузка `backend/.env` такого «чужого ключа» не даёт.

**Обезвреживание (предложение):**
1. **Подтвердить имя переменной** (ожидается `DB_PASSWORD`, файл — корневой `.env`) — без вывода значения. Это нужно, чтобы ротировать именно скомпрометированный секрет, а не весь набор.
2. **Ротация**: считать значение скомпрометированным и ротировать `DB_PASSWORD`; при использовании этого `.env` на реальном стенде — обязательно и с обновлением конфигурации деплоя (`docker-compose.yml:6`). Если подтвердится другое имя — ротировать его (`CHAINLIT_AUTH_SECRET` / `NETOPS_JWT_SECRET` / `NETOPS_ENCRYPTION_KEY` / `NETOPS_ZABBIX_TOKEN` — по обстоятельствам). Для `NETOPS_ENCRYPTION_KEY` ротация не «сменить строку», а перешифрование данных (процедура не описана — см. `.dsh/kb/30-deploy-and-env.md`, «Открытые вопросы»).
3. **Транскрипт**: не выгружать, не пересылать, не копировать в отчёты/тикеты; считать значение раскрытым в контекст модели-провайдера, т.е. компрометированным. Маскирование задним числом не помогает.
4. **Процессные правила** (чтобы не повторилось):
   - любой запуск Python, импортирующий `app.*`, выполнять с cwd = `backend/` (как в `docs/dev-checklist.md`, `.dsh/kb/00-overview.md`, `20-frontend.md`, `30-deploy-and-env.md`) либо из изолированного каталога **без** `.env`;
   - запретить ad-hoc `python -c`/`python -` пробы из корня репозитория: относительный `env_file=".env"` в `config.py` делает их опасными;
   - единственный санкционированный потребитель корневого `.env` — клиент `docker compose` (интерполяция `${VAR:?}` и `env_file`), не Python-код;
   - в импорт-пробах явно переопределять/очищать `NETOPS_*` и не полагаться на `.env`.
5. **Код-хардening** (владелец — `backend-dev`, вне моей зоны записи): добавить `extra="ignore"` в `SettingsConfigDict` (`backend/app/config.py:7`) — тогда чужой ключ из любого `.env` не будет печататься в тексте ошибки; безопасность от этого не снижается (лишние ключи и так не используются). Альтернатива/дополнение: в тестовом профиле передавать `_env_file=None`.

**Ответ на вопрос «предусматривает ли харнес запуск с корневым `.env`»:** инструкции харнеса **не** предписывают импорт `app.*` из корня. Проверено: `.dsh/kb/00-overview.md:95`, `.dsh/kb/20-frontend.md:98`, `.dsh/kb/30-deploy-and-env.md:134`, `docs/dev-checklist.md:54–58` используют `cd backend` (или `uvicorn` после `cd backend`); `run_tests.py` запускается из корня, но **сам `app` не импортирует**, а дочерние тесты стартуют с cwd = `backend/` или `chainlit/` (`run_tests.py:58–86`, `176–185`). Единственное штатное чтение корневого `.env` — `docker-compose.yml` (`env_file: .env`, `${VAR:?}`), и оно происходит в клиенте compose, а не в Python. **Системный риск** создаёт не инструкция, а относительный `env_file=".env"` + `extra='forbid'` в `backend/app/config.py:7`: любая ручная проба из корня повторяет инцидент. Зафиксировано как находка F-1 с предложением C4/C5.
