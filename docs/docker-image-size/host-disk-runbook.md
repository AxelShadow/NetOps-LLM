Правила работы с этим документом:

1. **Сначала доказательства — потом чистка.** Раздел 1 ничего не удаляет и выполняется целиком. Чистка (раздел 3) начинается только после того, как понятно, *какая именно* файловая система заполнена и *чем*.

## 0. Что именно означает исходная ошибка

Исходный вывод `docker compose up --build`:

```
Image netops-llm-app Building  1302.5s
failed to solve: failed to extract layer sha256:9d194c6df9ade50cb8470381779461964600d446439c67e6bf0fcd8467e63211:
write /var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/snapshots/475/fs/usr/local/lib/python3.11/site-packages/markdown_it/__pycache__/main.cpython-311.pyc:
no space left on device
```

Разбор по частям:

| Фрагмент | Что означает |
|---|---|
| `failed to solve` | Сборка идёт через BuildKit (в Docker 23+ он включён по умолчанию; `DOCKER_BUILDKIT=1` — то же самое). Ошибку вернул не `RUN` в Dockerfile, а инфраструктура сборки. |
| `failed to extract layer sha256:9d19…` | Слой **уже скачан** (blob лежит в content store), но не смог **распаковаться** в файловую систему. Диск кончился не на скачивании, а на распаковке. |
| `/var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/snapshots/475/fs/...` | Активен **containerd image store**: слои распаковываются в снапшоты containerd. Это **не** `/var/lib/docker`. Значит и заполненный раздел — тот, где смонтирован `/var/lib/containerd` (см. 1.3). |
| `usr/local/lib/python3.11/site-packages/markdown_it/...` | В распаковываемом слое лежит пакет `markdown_it` для **Python 3.11**, а `__pycache__/main.cpython-311.pyc` — байткод, скомпилированный интерпретатором 3.11. Аномалия разбирается в разделе 2. |
| `no space left on device` | `ENOSPC` от ядра при `write(2)`. Причина — **либо** кончились блоки, **либо** кончились inode. Текст ошибки в обоих случаях одинаковый (см. 0.2). |

### 0.1 Почему под сборку нужно в 2–3 раза больше места, чем «весит образ»

Одна и та же данные в процессе сборки существуют в нескольких копиях:

1. **Сжатый blob** слоя в content store (`/var/lib/containerd/io.containerd.content.v1.content`).
2. **Распакованный rootfs** того же слоя в снапшоте (`.../io.containerd.snapshotter.v1.overlayfs/snapshots/<N>/fs`). Распаковка даёт ещё одну копию, обычно в 2–3 раза больше сжатой.
3. **Новые слои** поверх (результат `pip install`), а также промежуточные слои BuildKit.
4. **Build cache** BuildKit — отдельные записи, которые живут независимо от образов и обычно занимают больше всего.
5. **Overlayfs copy-up**: при первой записи в файл из нижнего слоя overlayfs копирует файл в верхний слой целиком, т.е. запись «на несколько байт» может стоить места, равного размеру файла.

Практический вывод: **ошибка «в середине распаковки» — это классический признак того, что свободного места было «примерно столько же, сколько нужно», без запаса.** Планируйте запас 2–3× от суммы: базовые образы + новые слои + кэш сборки. Оценка для этого стека — в 4.1.

### 0.2 Нехватка inode даёт ровно тот же текст

Если на разделе кончились inode (файлов много, каждый мелкий), ядро всё равно возвращает `no space left on device`. При этом `df -h` будет показывать «свободно 20 G». Python-образы — это десятки тысяч мелких файлов на слой, а кэш сборки — миллионы. Поэтому **`df -i` обязателен**: без него можно освободить гигабайты и не понять, почему ошибка повторяется.

### 1.0. Сохранить выводы диагностики в каталог

```bash
# [ЧТЕНИЕ] Создать каталог для протокола в СВОЁМ домашнем каталоге. Ничего не удаляет.
# Почему не /root: перенаправления (`>`, `tee`) выполняет ваш shell, а не sudo, поэтому запись
# в /root без sudo даст "Permission denied".
WORK="$HOME/enospc-$(date +%F)"; mkdir -p "$WORK"; echo "WORK=$WORK"

# Ожидаемо: напечатан путь и данные той ФС, где он лежит. Если $HOME оказался на переполненном
# разделе (а его и разбираем), создайте каталог на другом разделе:
#   WORK="/mnt/<большой-раздел>/enospc-$(date +%F)"; mkdir -p "$WORK"; echo "WORK=$WORK"
# Дальше во всех шагах используется именно $WORK.
```

Дальше к любой команде можно добавить `2>&1 | tee -a "$WORK/diag.txt"`, чтобы протокол остался на хосте (если команда запускается через `sudo`, пишите `2>&1 | sudo tee -a "$WORK/diag.txt"`). Это удобно для разбора и для отчёта, но вывод всё равно не должен содержать секретов.


## 2. Шаг 2. Аномалия `python3.11` / `markdown_it`: откуда чужой слой

### 2.1. Что установлено локально (в репозитории) — и почему это важно

Проверено на текущей ревизии проекта:

* `backend/dockerfile` — `FROM python:3.12-slim`.
* `chainlit/Dockerfile` — `FROM python:3.12-slim`.
* Строки `python:3.11` / `3.11-slim` нет ни в файлах рабочего дерева, ни в истории git (`git log --all -S"python:3.11"` — пусто; `git log --all -S"python:3.12"` — 4 коммита).
* Пакета `markdown_it` нет ни в `backend/.venv`, ни в `chainlit/.venv`, и нет прямой зависимости в `backend/requirements.txt` / `chainlit/requirements.txt` (он приходит транзитивно, например через `rich` в зависимостях Chainlit).

Следствие: **базовый образ `python:3.12-slim` физически не может содержать `markdown_it` в `/usr/local/lib/python3.11/site-packages`.** Официальный slim-образ — это интерпретатор 3.12, pip и stdlib; никаких сторонних пакетов и никакого Python 3.11 там нет. Значит, нераспаковавшийся слой порождён **не** этой ревизией репозитория. Варианты — ниже, каждый проверяется командами.

### 2.2. Гипотезы и проверки

| # | Гипотеза | Как проверить | Что означает результат |
|---|---|---|---|
| H1 | На `<прод-хосте>` параллельно собирался/скачивался **другой** стек на Python 3.11, а ошибка попала в общий вывод `docker compose` | 2.3-A, 2.3-B, 1.7 | Если найден другой проект/образ с 3.11 и времена совпадают — виноват не netops-llm; лечится дисциплиной сборки (раздел 5) и местом (раздел 3/4). |
| H2 | В `<каталоге-деплоя>` лежит **другой/устаревший или изменённый** checkout (не HEAD `8ab0257`, dirty-дерево с правкой Dockerfile) | 2.3-C | Если `HEAD` ≠ `8ab0257` или `git status` показывает изменения в Dockerfile, а `grep` находит `python:3.11` — виноват код на хосте: обновить деплой до ревизии репозитория. |
| H3 | Тег `python:3.12-slim` во **внутреннем реестре/зеркале** указывает на образ, собранный поверх Python 3.11 (перетегирован) | 2.3-D | Если `PYTHON_VERSION` в метаданных образа = 3.11.x или в `docker history` видны лишние `RUN pip install` — тег скомпрометирован: пересобрать/перетегировать базовый образ, запретить сборку до исправления. |
| H4 | Рядом лежит **посторонний Dockerfile** с `FROM python:3.11`, который кто-то собирает на том же хосте | 2.3-E | Найденный файл + совпадение по времени = источник; согласовать с владельцем того стека. |
| H5 | Ошибка относится к **скачиванию** (pull) другого образа, а не к нашей сборке; строка `Image netops-llm-app Building` — просто ближайший контекст вывода | 2.3-F, 1.7 | Если слой принадлежит не нашему образу — наша сборка тут лишь «жертва» нехватки места; чистка и запас места решают проблему. |

### 2.3. Команды проверки

**A. Найти образ, которому принадлежит слой `sha256:9d194c…` (самое прямое доказательство)**

```bash
# [ЧТЕНИЕ] Перебрать все локальные образы и найти тот, в RootFS которого есть наш слой.
for i in $(docker images -q | sort -u); do
  docker image inspect "$i" --format '{{.Id}} {{.RepoTags}} {{join .RootFS.Layers " "}}'
done | grep -i 9d194c6df9ade50cb8470381779461964600d446439c67e6bf0fcd8467e63211
# Ожидаемо: одна строка — ID и теги образа, содержащего слой. Если строка найдена и это НЕ netops-llm-app
# (или образ вообще не из нашего стека) — гипотеза H5/H1 подтверждена: слой чужой.
# Если совпадений нет — слой либо уже вычищен сборщиком мусора, либо принадлежал pull, который не завершился.
```

**B. Кто ещё собирался/запущен на хосте**

```bash
# [ЧТЕНИЕ] Все compose-проекты и все контейнеры (включая остановленные).
docker compose ls -a
docker ps -a --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}\t{{.CreatedAt}}'
docker images --format 'table {{.Repository}}:{{.Tag}}\t{{.CreatedSince}}\t{{.Size}}' | grep -i -E "python|3\.11" | head -30
# Ожидаемо: список проектов/контейнеров/образов. Наличие образов с 3.11 в имени/теге или «чужих» проектов
# рядом с netops-llm — прямое подтверждение H1/H4.
```

**C. Проверка кода в каталоге деплоя**

```bash
# [ЧТЕНИЕ] Запускать в <каталоге-деплоя>.
cd <каталог-деплоя>
git rev-parse HEAD
git status --short
git log --oneline -5
grep -rn --include='Dockerfile' --include='dockerfile' --include='*.yml' --include='*.yaml' -E 'FROM +python:' .
git log --all -S"python:3.11" --oneline
# Ожидаемо: HEAD = 8ab0257bca70b934c8b8ef3291e16503069a96fd (проверенная ревизия), в git status --short
# НЕТ изменений ОТСЛЕЖИВАЕМЫХ файлов (untracked-файлы допустимы — на проде они вполне могут быть),
# grep показывает только python:3.12-slim, git log -S"python:3.11" — пусто.
# ЛЮБОЕ отклонение = деплой не соответствует репозиторию (H2):
#   * другой HEAD → обновить/сверить деплой;
#   * dirty-правки Dockerfile → выяснить, кто и зачем правил;
#   * найденный python:3.11 → источник аномалии найден, согласовать с владельцем.
```

**D. Проверка, что за образ скрывается за тегом `python:3.12-slim` (без запуска контейнера)**

```bash
# [ЧТЕНИЕ] Метаданные образа: официальный python-образ публикует ENV PYTHON_VERSION.
docker image inspect python:3.12-slim --format '{{.Id}} {{.RepoTags}} {{.RepoDigests}} {{.Created}}'
docker image inspect python:3.12-slim --format '{{range .Config.Env}}{{println .}}{{end}}' | grep -i -E 'python|version'
# Ожидаемо: PYTHON_VERSION=3.12.x (для 3.12-slim это 3.12.*).
# Если выводится 3.11.x ЛИБО ENV с Python/PATH, ведущими в 3.11 — тег перетегирован (H3).
```

```bash
# [ЧТЕНИЕ] История слоёв: у официального slim-образа нет слоёв с ручным pip install.
docker history --no-trunc python:3.12-slim | head -30
# Ожидаемо: несколько слоёв базового debian + установка Python из исходников/пакетов.
# Лишние слои вида "RUN /bin/sh -c pip install ..." или "COPY ... site-packages" = кто-то собрал свой образ
# и выложил его под официальным тегом (H3). Сборку до исправления не возобновлять.
```

```bash
# [ЧТЕНИЕ, ОПЦИОНАЛЬНО] Если всё же нужно увидеть версию «внутри» — запускается контейнер, но ничего не меняет.
docker run --rm --entrypoint python python:3.12-slim -V
# Ожидаемо: "Python 3.12.x". Если 3.11.x — H3 подтверждена.
# Требуется свободное место под создание контейнера; на переполненном диске может не запуститься.
```

**E. Поиск посторонних Dockerfile с Python 3.11 на хосте**

```bash
# [ЧТЕНИЕ] Может идти минуту-две.
sudo find / -xdev -type f \( -name 'Dockerfile' -o -name 'Dockerfile.*' -o -name 'dockerfile' \) \
  -not -path '*/.git/*' -not -path '*/node_modules/*' 2>/dev/null > /tmp/dockerfiles.txt
sudo xargs -r grep -nE 'FROM +python:3\.11' < /tmp/dockerfiles.txt
# Ожидаемо: пусто. Если строки есть — в <путь>:<номер строки> указан владелец постороннего стека (H4):
# сравните время его сборки с временем инцидента (1.7).
```

**F. Отличить нашу сборку от чужого pull по времени**

```bash
# [ЧТЕНИЕ] Когда началась сборка netops-llm-app и что происходило в те же секунды.
sudo journalctl -u docker --since "24 hours ago" --no-pager \
  | grep -i -E "netops-llm|extract|pull|no space" | tail -100
# Ожидаемо: последовательность операций с временными метками.
# Если "no space" стоит рядом с pull чужого образа — это H5.
```

### 2.4. Как читать результаты

| Наблюдение | Вывод | Действие |
|---|---|---|
| Слой `9d194c…` принадлежит образу другого проекта | Аномалия не из netops-llm (H5/H1) | Наша сборка не виновата: освободить место (раздел 3), развести сборки по времени (раздел 5), уведомить владельца чужого стека. |
| HEAD в `<каталоге-деплоя>` ≠ `8ab0257` или Dockerfile изменён | Деплой не соответствует репозиторию (H2) | Обновить `<каталог-деплоя>` до проверенной ревизии, повторить диагностику. |
| `PYTHON_VERSION=3.11.x` у `python:3.12-slim` | Тег перетегирован (H3) | Остановить сборки, уведомить владельца реестра, восстановить корректный базовый образ; до этого сборки не запускать. |
| Найден посторонний Dockerfile с `python:3.11` | Рядом живёт чужой стек (H4) | Согласовать порядок сборок/квоты, следить за местом. |
| Ничего из перечисленного не найдено, слой отсутствует | Источник уже «затёрт» (сборщик мусора, повторный pull) | Зафиксировать как неопределённость; продолжить с раздела 3 — на устранение ENOSPC это не влияет. |

**Чего делать не нужно:** гадать по имени пакета. `markdown_it` — это транзитивная зависимость Python-экосистемы (например, через `rich`), она встречается в сотнях стеков; сам факт её наличия не указывает на netops-llm. Указывает только **интерпретатор 3.11** и то, какому образу принадлежит слой (2.3-A).

## 3. Шаг 3. Безопасное освобождение места (по возрастанию риска)

Раздел выполняется **после** раздела 1. Останавливайтесь, как только места стало достаточно с запасом 2–3× (раздел 4.1): каждый следующий шаг рискованнее предыдущего.

### 3.0. Предварительное условие: подтверждённая резервная копия БД

Прежде чем удалять что-либо, убедитесь, что данные PostgreSQL сохранены **вне** диска, который чистите.

```bash
# [ЧТЕНИЕ] Найти том с данными PostgreSQL и его точку монтирования.
cd <каталог-деплоя>
docker volume ls | grep -i pgdata
docker volume inspect netops-llm_pgdata --format '{{.Name}} {{.Driver}} {{.Mountpoint}}'
# Ожидаемо: имя вида netops-llm_pgdata (префикс — имя compose-проекта, выводится из имени каталога деплоя).
# Если проекта ещё нет/имя другое — используйте фактическое имя из docker volume ls.
# Наличие Mountpoint (например, /var/lib/docker/volumes/netops-llm_pgdata/_data) говорит, где физически лежат данные.
```

```bash
# [ЧТЕНИЕ+БЕЗОПАСНО] Проверить, что контейнер БД работает и дамп снимается.
docker compose ps
# Дамп пишем в $WORK из шага 1.0 (перенаправление выполняет ваш shell — в /root без sudo будет отказано).
docker compose exec -T db pg_dump -U netops -Fc netops > "$WORK/netops-backup-$(date +%F).dump"
ls -lh "$WORK"/netops-backup-*.dump
docker run --rm -v "$WORK":/backup postgres:16-alpine pg_restore --list "/backup/netops-backup-$(date +%F).dump" | head
# Ожидаемо: файл дампа ненулевого размера; pg_restore --list печатает оглавление архива (без данных).
# Если pg_dump не работает из-за нехватки места — сначала освободите немного места (3.2/3.3, они безопасны),
# затем повторите дамп, и только после этого переходите к деструктивным шагам.
# Если docker требует sudo (оператор не в группе docker), перенаправление всё равно должно выполняться
# вашим shell — выносим docker внутрь sh:
#   sudo sh -c 'docker compose exec -T db pg_dump -U netops -Fc netops' > "$WORK/netops-backup-$(date +%F).dump"
# ⚠️ Файл дампа содержит данные БД. Не копируйте его в тикеты и не выкладывайте наружу.
```

```bash
# [СОХРАНЕНИЕ] Скопировать дамп за пределы <прод-хоста> (на бэкап-хранилище) ДО чистки.
scp "$WORK/netops-backup-$(date +%F).dump" <бэкап-хост>:<путь>/
# Ожидаемо: файл скопирован. Без подтверждённой копии деструктивные шаги (3.5+) не выполняются.
```

Дополнительно: если есть возможность снять снапшот ВМ/LV — сделайте это. Снапшот не заменяет дамп БД, но даёт «точку отката» для всей файловой системы.

### 3.1. Остановленные контейнеры

```bash
# [ЧТЕНИЕ] Сколько остановленных контейнеров и сколько места они держат.
docker ps -a --filter status=exited --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}\t{{.Size}}'
docker system df -v | sed -n '/^Containers space usage/,/^$/p'
# Ожидаемо: список остановленных контейнеров. Каждый держит свой записываемый слой.
```

```bash
# [⚠️ ДЕСТРУКТИВНО] Удаление остановленных контейнеров.
docker container prune --force
# Что теряется: остановленные контейнеры и их записываемые слои (включая логи контейнера и любые данные,
# записанные ВНУТРЬ контейнера, а не в том). Тома (pgdata, devdata) НЕ удаляются.
# Как восстановить: контейнеры пересоздаются из образов (docker compose up -d). Данные в томах сохраняются.
# Нужен ли бэкап: для netops-llm не обязателен (данные в томе pgdata), но перед выполнением убедитесь,
# что в списке нет контейнеров, чьи данные вам нужны. Сомневаетесь — сначала 3.2 и 3.3 (они безопасны).
# Ожидаемо: строка "Total reclaimed space: X" с объёмом. Повторить: df -h.
```

### 3.2. Кэш сборки BuildKit (самый безопасный способ освободить много места)

```bash
# [ЧТЕНИЕ] Сколько занимает кэш, если активен отдельный builder.
docker system df -v | sed -n '/^Build cache usage/,/^$/p'
# [ЧТЕНИЕ, ОПЦИОНАЛЬНО] Кэш выбранного builder'а, если установлен плагин buildx.
docker buildx version && docker buildx du | tail -5
# Ожидаемо: строка Build cache с объёмами (в т.ч. reclaimable). Отсутствие docker buildx — не ошибка: пропустите (плагин
# поставляется отдельно; в Docker 24.0.6 он может отсутствовать/быть несовместим).
```

```bash
# [БЕЗОПАСНО ДЛЯ ДАННЫХ] Обрезать кэш до лимита: удаляются только самые старые записи кэша.
docker builder prune --force --keep-storage 5GB
# Что теряется: только записи build cache (промежуточные результаты сборки) сверх 5 GB. Образы и тома не трогаются.
# Восстановление: не требуется — следующий build просто пересоберёт слои с нуля (дольше, больше трафика).
# Нужен ли бэкап: нет. Кэш — восстанавливаемый артефакт.
# Ожидаемо: "Total reclaimed space: X".
```

```bash
# [БЕЗОПАСНО ДЛЯ ДАННЫХ] Если места всё ещё мало — удалить кэш целиком.
docker builder prune --force
# Что теряется: весь build cache. Образы, контейнеры и тома не затрагиваются.
# Следствие: следующая сборка выполнит все pip install заново. Данные не теряются. Бэкап не нужен.
# Ожидаемо: итоговый "Total reclaimed space".
```

```bash
# [БЕЗОПАСНО ДЛЯ ДАННЫХ] Точечно: удалить только кэш старше N часов (например, 24).
docker builder prune --force --filter "until=24h"
# Ожидаемо: меньше освобождённого объёма, но сохраняется свежий кэш → следующая сборка быстрее.
# Версия/наличие флагов проверяются локально: docker builder prune --help (см. раздел 9).
```

### 3.3. «Висячие» (dangling) образы и слои

```bash
# [ЧТЕНИЕ] Список dangling-образов.
docker images --filter dangling=true --format 'table {{.ID}}\t{{.Size}}\t{{.CreatedSince}}'
# Ожидаемо: обычно несколько промежуточных слоёв без тега.
```

### 3.4. Неиспользуемые образы (в том числе с тегами)

```bash
# [ЧТЕНИЕ] Какие образы будут затронуты: не используемые ни одним контейнером.
docker images --format '{{.Repository}}:{{.Tag}}\t{{.ID}}\t{{.Size}}\t{{.CreatedSince}}' | sort -k3 -rh | head -30
docker system df -v | sed -n '/^Images space usage/,/^$/p' | head -40
# Ожидаемо: список кандидатов. Обратите внимание: в списке будут и базовые образы
# (python:3.12-slim, nginx:alpine, postgres:16-alpine), если контейнеры сейчас не запущены.
```

```bash
# [⚠️ ДЕСТРУКТИВНО, мягкий вариант] Удалить неиспользуемые образы старше 7 дней.
docker image prune --all --force --filter "until=168h"
# Что теряется: все образы БЕЗ тега И с тегом, не используемые ни одним контейнером и созданные раньше 7 суток.
# Данные в томах (pgdata) НЕ затрагиваются: тома живут отдельно от образов.
# Что это значит на практике: следующая сборка заново скачает базовые образы (нужен доступ к реестру/зеркалу!)
# и пересоберёт слои. Время сборки вырастет, разово вырастет и потребление трафика.
# Как восстановить: образы пересобираются/перекачиваются из реестра. Если реестр недоступен — восстановить НЕЛЬЗЯ.
# Нужен ли бэкап: да, проверьте доступность реестра/mirror'а ДО запуска; дамп БД из 3.0 обязателен.
# Ожидаемо: "Total reclaimed space" и список удалённых тегов.
# ПРОВЕРКА ПЕРЕД ЗАПУСКОМ (обязательно): убедиться, что в списке нет образа, который нельзя перекачать.
docker image ls --filter reference='*netops*'
```

```bash
# [⚠️ ДЕСТРУКТИВНО, жёсткий вариант] Удалить ВСЕ неиспользуемые образы (кроме тех, чей контейнер запущен/остановлен).
docker image prune --all --force
# Что теряется: базовые образы, старые сборки, вообще все образы без связанных контейнеров.
# Восстановление: только повторный pull/build. Бэкап не поможет — образы не бэкапятся.
# Запускать, только если 3.2 и 3.3 не дали нужного результата И реестр доступен.
```

### 3.5. Точечное удаление конкретных крупных образов (вместо «удалить всё»)

```bash
# [ЧТЕНИЕ] Крупнейшие образы с ID.
docker images --format '{{.Size}}\t{{.ID}}\t{{.Repository}}:{{.Tag}}\t{{.CreatedSince}}' | sort -rh | head -20
# [ЧТЕНИЕ] Используется ли кандидат контейнером.
docker ps -a --filter ancestor=<IMAGE_ID> --format 'table {{.Names}}\t{{.Status}}'
# Ожидаемо: пусто = образ не занят; можно удалять точечно.

# [⚠️ ДЕСТРУКТИВНО] Удаление одного конкретного образа.
docker rmi <IMAGE_ID>
# Что теряется: именно этот образ и его слои (если на них не ссылаются другие образы).
# Восстановление: pull/build из реестра. Тома не затрагиваются. Бэкап не требуется.
# Ожидаемо: "Deleted: sha256:..." по слоям либо "image is being used by ..." (тогда образ занят — не удаляйте).
```

```bash
# [ЧТЕНИЕ] Инвентаризация томов: что есть и где лежит.
docker volume ls
# По каждому тому, который выглядит ненужным, — ОТДЕЛЬНАЯ проверка, по одному тому:
docker volume inspect <VOLUME_NAME> --format '{{.Name}} driver={{.Driver}} mountpoint={{.Mountpoint}}'
docker ps -a --filter volume=<VOLUME_NAME> --format 'table {{.Names}}\t{{.Status}}'
# Ожидаемо: если docker ps -a показывает контейнер с этим томом — том занят, удалять нельзя.

# [🔴 ЗАПРЕЩЕНО] Эти команды удаляют и ИМЕНОВАННЫЕ неиспользуемые тома — включая netops-llm_pgdata,
# если контейнер db в этот момент не существует (после docker compose down, перезагрузки, аварии):
# docker volume prune --all --force
# docker volume prune -a
# docker system prune -a --volumes
# У `docker volume prune --all` нет механизма «исключить один том»: поштучный разбор выше от неё
# НЕ защищает. Том netops-llm_pgdata в рамках этого ранбука не удаляется вообще.

# [⚠️ ДЕСТРУКТИВНО — только по одному тому и только после бэкапа] Если том ТОЧНО не нужен:
docker volume rm <VOLUME_NAME>
# Что теряется: данные ИМЕННО этого тома, безвозвратно (образы и другие тома не затрагиваются).
# Восстановление: только из дампа (3.0) или из бэкапа тома. Дамп БД должен быть снят И выгружен наружу.
# Нужен ли бэкап: ОБЯЗАТЕЛЬНО. Перед запуском: (1) свежий выгруженный дамп/бэкап тома,
# (2) вывод docker volume inspect и docker ps -a --filter volume=<VOLUME_NAME> из блока выше,
# (3) осознанное решение по ИМЕННО этому тому.
# НЕ трогать тома проектов, данные которых нужны (netops-llm_pgdata; devdata — только dev-стенд).
# Ожидаемо: напечатано имя удалённого тома. Ошибка "volume is in use" — это защита, а не сбой.
```

### 3.6. Перезапуск демонов, чтобы сборщик мусора вернул неиспользуемые данные

Важно: перезапуск `docker.service` сам по себе **не** перезапускает `containerd.service` (тот может быть запущен отдельно или socket-activated), поэтому форсированная сборка мусора containerd и снятие зависших leases при этом не гарантированы. Ниже два варианта: сначала мягкий (только Docker), затем — при необходимости — жёсткий (containerd).

```bash
# [РИСК: КРАТКОВРЕМЕННЫЙ ПРОСТОЙ] Вариант 1 (мягкий): перезапуск Docker.
sudo systemctl restart docker
sudo systemctl status docker --no-pager | head -5
# Что происходит: контейнеры останавливаются и (благодаря restart: unless-stopped) поднимаются снова;
# проверяется, что демон стартует. Данные не теряются (тома на месте).
# Что НЕ происходит: containerd.service не перезапускается → сборка мусора containerd и снятие leases
# могут не выполниться (containerd собирает мусор периодически и сам). Если df после этого не изменился —
# переходите к варианту 2.
# Требует окна: короткий простой сервисов. Бэкап: дамп БД из 3.0 (на случай, если контейнер не поднимется).
# Ожидаемо: active (running). Проверить: docker ps, docker system df, df -h, df -i.
```

```bash
# [РИСК: КРАТКОВРЕМЕННЫЙ ПРОСТОЙ] Вариант 2 (жёсткий): перезапуск containerd, затем Docker.
# ⚠️ ВНИМАНИЕ: перезапуск containerd затрагивает ВСЕ контейнеры хоста, включая чужие проекты и сервисы.
# Выполняйте только в согласованное окно и предупредив владельцев остальных стеков на хосте.
sudo systemctl stop docker.socket docker
sudo systemctl restart containerd
sudo systemctl start docker
systemctl status containerd docker --no-pager | head -10
# Порядок обязателен: сначала containerd, затем docker (docker подключается к containerd при старте).
# Ожидаемо: оба active (running); docker ps показывает контейнеры; df -h / df -i показывают освобождение.
```

### 3.7. 🔴 Что именно уничтожает том `pgdata` (и почему это запрещено)

Том `netops-llm_pgdata` — это **данные PostgreSQL** (`pgdata:/var/lib/postgresql/data` в `docker-compose.yml`). Команды ниже удаляют его безвозвратно, если контейнер `db` в момент запуска не существует (после `docker compose down`, перезагрузки, аварийного останова). Восстановить данные можно только из дампа/бэкапа; `docker` не спрашивает «это точно ваша прод-база?» — он спрашивает один раз «Are you sure?» и удаляет.

**Главные «убийцы» тома, в порядке частоты ошибок:**

1. `docker volume prune --all` — по документации и по `--help` Docker 24.x: «Remove all unused volumes, not just anonymous ones», т. е. **именованные** тома тоже. Механизма «исключить один конкретный том» у команды нет.
2. `docker compose down -v` — флаг `-v` удаляет тома проекта. На проде допустим только `docker compose down` **без** `-v`; `-v` — это сброс данных, он описан в `docs/dev-checklist.md` и предназначен исключительно для dev-стенда.
3. `docker system prune -a --volumes` — с точной оговоркой: в Docker 24.x флаг `--volumes` документирован как «Prune anonymous volumes» (анонимные тома), и текст подтверждения говорит про «anonymous volumes not used by at least one container». **Однако** в примерах той же официальной документации v24.0.6 показано удаление **именованного** тома, т. е. поведение неоднозначно. Предсказать результат однозначно нельзя → на проде команда запрещена (консервативно), тем более что вместе с `--all` она вычищает ещё и все неиспользуемые образы с кэшем.

```bash
# [🔴 ЗАПРЕЩЕНО] НЕ ВЫПОЛНЯТЬ на <прод-хосте> с прод-данными:
# docker volume prune --all --force      # удаляет и именованные тома, включая netops-llm_pgdata
# docker volume prune -a
# docker compose down -v                 # -v = удаление томов проекта (pgdata), это dev-операция
# docker system prune -a --volumes       # --volumes описан как «anonymous», но примеры в доке
#                                        # v24.0.6 показывают именованный том → не рискуем
# docker system prune --all --volumes --force
```

**Безопасная альтернатива** (порядок из этого раздела, по возрастанию риска):

1. `docker builder prune --force --keep-storage 5GB` → затем `docker builder prune --force` (3.2).
2. `docker image prune --force` (3.3, только dangling).
3. `docker image prune --all --force --filter "until=168h"` (3.4, с проверкой доступности реестра).
4. `docker rmi <IMAGE_ID>` точечно по самым крупным неиспользуемым образам (3.5).
5. `sudo systemctl restart docker`, при необходимости — вариант 2 с перезапуском `containerd` (3.6); затем снова `df -h` / `df -i`.
6. И только если места всё ещё не хватает: `docker volume ls` → по каждому тому `docker volume inspect <NAME>` + `docker ps -a --filter volume=<NAME>` → свежий выгруженный дамп → осознанное решение по **каждому** тому отдельно → `docker volume rm <NAME>` (по одному). Том `netops-llm_pgdata` в рамках этого ранбука не удаляется вообще. Команды `docker volume prune --all`, `docker compose down -v` и `docker system prune -a --volumes` не используются ни на одном шаге.

### 3.8. Что делать, если места уже нет даже на чистку

3.8.1. Если демон не отвечает (`docker info` → `cannot connect`), сначала освободите «внешнее» место: перенесите/удалите ненужные крупные файлы из 1.6, почистите журнал systemd:

```bash
# [⚠️ ДЕСТРУКТИВНО для истории журнала] Обрезать системный журнал до 500 MB.
sudo journalctl --vacuum-size=500M
# Что теряется: старые записи journald (в том числе логи предыдущих разборов). Данные приложений не затрагиваются.
# Восстановление: невозможно (журнал не бэкапится штатно).
# Нужен ли бэкап: если журнал нужен для разбора — сохраните нужные записи заранее:
#   sudo journalctl -u docker --since "7 days ago" --no-pager > "$WORK/docker-journal.txt"
# Ожидаемо: "Vacuuming done, freed X of archived journals".
```

3.8.2. Затем `sudo systemctl restart containerd docker` и снова `docker system df -v`, `df -h`, `df -i`.

3.8.3. Если и это невозможно — переходите к разделу 4 (перенос/расширение раздела).

### 3.9. Проверка после чистки

```bash
# [ЧТЕНИЕ] Обязательное подтверждение результата.
```

## 4. Шаг 4. Если места физически мало

Признак того, что дело не в мусоре: после разделов 3.2–3.6 `df -h` показывает, что свободного места на разделе объективно меньше, чем нужно сборке (см. 4.1).

### 4.1. Сколько места нужно

Оценка для этого стека (собираются два образа: `app` и `chainlit`, оба от `python:3.12-slim`; для запуска дополнительно нужны `postgres:16-alpine` и `nginx:alpine`):

| Компонент | Порядок величины |
|---|---|
| Сжатые базовые образы (в content store) | единицы сотен MB |
| Распакованные rootfs базовых образов | ≈ 0.5–1.0 GB |
| Новые слои сборки (backend: pyvmomi, cryptography, pysnmp; chainlit: chainlit, httpx) | ≈ 0.5–1.5 GB |
| Пик build cache BuildKit | может достигать нескольких GB |
| Overlayfs-копии при copy-up | десятки MB … сотни MB |

**Практическое правило:** перед сборкой на разделе с `/var/lib/containerd` должно быть свободно **не менее ~10 GB** (комфортно — **15–20 GB**), причём проверять надо и блоки, и inode. Это оценка, а не измерение на прод-хосте: точные цифры получаются так:

```bash
# [ЧТЕНИЕ] Сколько суммарно занимают имеющиеся образы и кэш (нижняя граница потребности).
docker system df
# [ЧТЕНИЕ] Сколько свободно сейчас.
df -h /var/lib/containerd; df -i /var/lib/containerd
# Ожидаемо: сопоставив эти два вывода, вы понимаете, хватает ли места «в один образ» или нужно расширение.
```

### 4.2. Можно ли обойтись расширением раздела (наименее рискованный путь)

```bash
# [ЧТЕНИЕ] Есть ли свободное место в группе томов и какой ФС растить.
sudo vgs
sudo lvs -o lv_name,vg_name,lv_size
findmnt -T /var/lib/containerd -o TARGET,SOURCE,FSTYPE
# Ожидаемо: если у vgs в столбце VFree есть гигабайты, а TARGET указывает на логический том —
# расширение возможно без новых дисков и без переноса данных (4.3).
```

### 4.3. Вариант A: расширить логический том и файловую систему

```bash
# [РИСК: НИЗКИЙ, но необратимый по размеру] Расширение LV и ФС.
sudo lvextend -L +20G /dev/<VG>/<LV>
sudo resize2fs /dev/<VG>/<LV>      # для ext4
# либо, для XFS (XFS растёт только на смонтированной ФС):
sudo xfs_growfs <точка-монтирования>
# Что происходит: раздел становится больше. Данные НЕ удаляются, но откатить уменьшение сложно/невозможно.
# Бэкап: рекомендуется (снапшот ВМ/LV), потому что это изменение геометрии ФС.
# Ожидаемо: lvextend — "Logical volume <LV> successfully resized"; resize2fs/xfs_growfs — успешное завершение.
# Проверка: df -h <точка-монтирования> показывает новый размер.
```

### 4.4. Вариант B: перенести data-root Docker на больший раздел

```bash
# [ЧТЕНИЕ] Где сейчас data-root.
docker info --format '{{.DockerRootDir}}'
df -h "$(docker info --format '{{.DockerRootDir}}')"
# Ожидаемо: /var/lib/docker и его ФС. Если активен containerd image store (раздел 2), большие данные
# могут лежать не здесь, а в /var/lib/containerd — тогда смотрите 4.5.
```

Порядок переноса (выполнять в окно простоя, **обязательно** с бэкапом):

> ⚠️ Перед началом проверьте, какой backend активен: `docker info -f '{{.DriverStatus}}'`.
> Если это containerd image store (`[[driver-type io.containerd.snapshotter.v1]]`, см. раздел 2), то слои образов лежат в `/var/lib/containerd`, а перенос одного лишь `data-root` их **не** перенесёт — в этом случае нужен вариант 4.5. Перенос `data-root` переносит тома и остальное содержимое store, но не containerd-хранилище слоёв.
> ⚠️ `/etc/docker/daemon.json` в этом варианте **дополняется**, а не перезаписывается: потеря ключа `features.containerd-snapshotter` молча меняет storage backend, после чего Docker «не видит» образы и тома, а `docker compose up` создаёт **новый пустой** том `pgdata` (PostgreSQL инициализирует пустую БД). Это выглядит как потеря прод-данных, хотя данные остаются в прежнем store.

```bash
# [⚠️ ДЕСТРУКТИВНО / ВЫСОКИЙ РИСК] Перенос data-root. Каждый шаг — осознанно.
# 0) Бэкап: дамп БД (3.0) снят И выгружен наружу; по возможности — снапшот ВМ/LV.
# 1) Смонтировать целевой раздел и проверить, что на нём достаточно места.
df -h <целевой-раздел>
# 2) Остановить docker (и его сокет, чтобы не перезапустился сам).
sudo systemctl stop docker.socket docker
# 3) Скопировать данные с сохранением прав/владельцев/xattr.
sudo rsync -aHAX --numeric-ids --info=progress2 /var/lib/docker/ /<новый-путь>/docker/
# 4) Убедиться, что скопировалось (объёмы должны быть сопоставимы).
sudo du -xsh /var/lib/docker /<новый-путь>/docker
# 5) СНАЧАЛА посмотреть текущий конфиг целиком и сохранить бэкап. НЕ перезаписывать файл!
sudo ls -l /etc/docker/daemon.json
sudo cat /etc/docker/daemon.json
# Ожидаемо: на этом хосте в файле есть как минимум "features": { "containerd-snapshotter": true }
# (см. раздел 2). Там же могут быть registry-mirrors (критично для последующих pull), log-driver,
# bip, dns и другие ключи — ВСЕ они должны сохраниться. Если файла нет — это тоже нормально.
sudo cp -a /etc/docker/daemon.json /etc/docker/daemon.json.bak-$(date +%F) 2>/dev/null || echo "daemon.json отсутствует — бэкапить нечего"
# 5a) ДОПОЛНИТЬ конфиг: добавить/заменить ТОЛЬКО ключ data-root.
# ВАЖНО: /etc/docker/daemon.json устанавливается ТОЛЬКО после успеха ВСЕХ проверок ниже.
# Редирект `>` усекает целевой файл ДО запуска команды, поэтому «вслепую» копировать результат
# в системный конфиг нельзя: пустой daemon.json = старт Docker без features.containerd-snapshotter
# = подмена storage backend = пустой том pgdata при `docker compose up`.
if command -v jq >/dev/null; then
  if sudo test -f /etc/docker/daemon.json; then
    sudo jq '. + {"data-root": "/<новый-путь>/docker"}' /etc/docker/daemon.json > /tmp/daemon.json.new \
      || { echo "GATE FAIL: jq не отработал — правку НЕ применять, СТОП"; }
  else
    printf '{\n  "data-root": "/<новый-путь>/docker"\n}\n' > /tmp/daemon.json.new
  fi
  if sudo test -s /tmp/daemon.json.new \
     && sudo grep -q '"data-root"' /tmp/daemon.json.new \
     && python3 -m json.tool /tmp/daemon.json.new >/dev/null; then
    # install, а не `cp -a`: не переносим владельца/права из /tmp на системный конфиг.
    sudo install -m 644 -o root -g root /tmp/daemon.json.new /etc/docker/daemon.json
    echo "OK: daemon.json обновлён (data-root добавлен/заменён)"
  else
    echo "GATE FAIL: результат jq пуст / не JSON / без data-root — /etc/docker/daemon.json НЕ изменён, СТОП"
  fi
else
  echo "jq не установлен: отредактируйте /etc/docker/daemon.json ВРУЧНУЮ (sudo vi), сохранив ВСЕ прежние ключи"
fi
sudo cat /etc/docker/daemon.json
# ГЕЙТ 5 (машинный, обязателен ДО шага 6): data-root задан. Если нет — шаг 6 (mv, необратимый) НЕ выполняется.
if sudo grep -q '"data-root"' /etc/docker/daemon.json; then
  echo "OK: data-root задан — можно переходить к шагу 6"
  # 6) Переименовать (НЕ удалять!) старый каталог — это точка отката.
  sudo mv /var/lib/docker /var/lib/docker.old-$(date +%F)
else
  echo "GATE FAIL: data-root не задан — СТОП: шаг 6 (mv каталога) НЕ выполнять, шаг 7 (запуск Docker) не выполнять; вернуться к 5a"
fi
# Дополнительная проверка сохранности прежних ключей: при containerd image store ключ обязателен.
sudo grep -q 'containerd-snapshotter' /etc/docker/daemon.json \
  && echo "OK: features.containerd-snapshotter на месте" \
  || echo "ВНИМАНИЕ: ключ containerd-snapshotter в daemon.json не найден. Если хост использует containerd image store (раздел 2) — это СТОП: разберитесь до шага 7."
# 7) ГЕЙТ: запустить docker и убедиться, что backend хранения НЕ подменился и данные видны.
sudo systemctl start docker
docker info -f '{{.DriverStatus}}'
# Ожидаемо: [[driver-type io.containerd.snapshotter.v1]] — то же, что было ДО правки.
# Машинная проверка backend (ГЕЙТ 7a): печатаем значение и сверяем строку.
docker info -f '{{.DriverStatus}}' | grep -q 'io.containerd.snapshotter.v1' \
  && echo "OK: backend хранения не подменён" \
  || { echo "GATE FAIL: backend хранения изменился — СТОП, немедленный откат (см. ниже), compose НЕ поднимать"; }
# Если видите overlay2 (или driver-type отсутствует) — СТОП, немедленный откат:
#   sudo systemctl stop docker.socket docker
#   sudo cp -a /etc/docker/daemon.json.bak-<дата> /etc/docker/daemon.json
#   sudo mv /var/lib/docker.old-<дата> /var/lib/docker
#   sudo systemctl start docker
docker info --format 'DockerRootDir={{.DockerRootDir}}'
# Машинная проверка пути (ГЕЙТ 7b): DockerRootDir должен быть РОВНО новым путём.
docker info --format '{{.DockerRootDir}}' | grep -qx '/<новый-путь>/docker' \
  && echo "OK: DockerRootDir = /<новый-путь>/docker" \
  || { echo "GATE FAIL: DockerRootDir не совпадает с ожидаемым — СТОП, откат, compose НЕ поднимать"; }
docker images
docker volume ls
docker system df -v
docker ps -a
# СТОП-УСЛОВИЕ: если `docker images` пуст, либо в `docker volume ls` нет тома с pgdata, либо
# DriverStatus не содержит io.containerd.snapshotter.v1 — НЕ запускать `docker compose up` / `up -d`:
# compose создаст ПУСТОЙ том pgdata, и Postgres инициализирует пустую БД. Сначала откат и диагностика.
# 8) Только после успешной проверки (образы и тома на месте, контейнеры запускаются) — удалить старый
#    каталог, отдельным решением и позже: sudo rm -rf /var/lib/docker.old-<дата>
# ОТКАТ (полный): остановить docker, вернуть прежний daemon.json из бэкапа, вернуть каталог:
#   sudo systemctl stop docker.socket docker
#   sudo cp -a /etc/docker/daemon.json.bak-<дата> /etc/docker/daemon.json
#   sudo rm -rf /var/lib/docker              # ← только если каталог создан заново и пуст/не нужен
#   sudo mv /var/lib/docker.old-<дата> /var/lib/docker
#   sudo systemctl start docker
# Что теряется при ошибке: образы и тома остаются в СТАРОМ каталоге; при неверном data-root docker
# создаёт НОВЫЙ ПУСТОЙ store и «не видит» данные — именно поэтому гейт 7 обязателен ДО запуска compose.
# Данные не пропадают: старый каталог переименован, а не удалён.
# Нужен ли бэкап: да — дамп БД обязателен, снапшот ВМ/LV настоятельно рекомендуется.
```

### 4.5. Вариант C: перенести корень containerd (случай из нашего лога)

Путь из ошибки указывает на containerd store, значит переносить нужно **его**.

```bash
# [ЧТЕНИЕ] Текущий root/state containerd.
sudo grep -nE '^[[:space:]]*(root|state)[[:space:]]*=' /etc/containerd/config.toml
containerd config dump | grep -E '^[[:space:]]*(root|state)' | head
# Ожидаемо: root = "/var/lib/containerd" (или иной путь — вот его и нужно переносить),
# state = "/run/containerd" (переносить НЕ нужно, это рантайм-состояние).
# Замечание: root может быть задан и в drop-in, поэтому перед правкой смотрите фактическое значение
# из `containerd config dump` (он показывает результат слияния всех конфигов).
```

```bash
# [⚠️ ДЕСТРУКТИВНО / ВЫСОКИЙ РИСК] Перенос корня containerd.
# 0) Бэкап: дамп БД (3.0) + снапшот ВМ/LV. Это обязательное условие.
# 1) Остановить docker, затем containerd (именно в таком порядке).
sudo systemctl stop docker.socket docker
sudo systemctl stop containerd
# 2) Скопировать данные.
sudo rsync -aHAX --numeric-ids --info=progress2 /var/lib/containerd/ /<новый-путь>/containerd/
sudo du -xsh /var/lib/containerd /<новый-путь>/containerd
# 3) Изменить root в конфиге containerd — толерантно к форматированию (root = "…", root="…", отступы).
sudo cp -a /etc/containerd/config.toml /etc/containerd/config.toml.bak-$(date +%F)
sudo sed -i -E 's|^[[:space:]]*root[[:space:]]*=.*|root = "/<новый-путь>/containerd"|' /etc/containerd/config.toml
# 3a) ЖЁСТКИЙ ГЕЙТ по ЭФФЕКТИВНОМУ значению: root может приходить из drop-in
# (/etc/containerd/conf.d/*.toml), поэтому проверяем результат слияния (`containerd config dump`),
# а не только текст основного файла.
sudo grep -nE '^[[:space:]]*root[[:space:]]*=' /etc/containerd/config.toml
containerd config dump | grep -nE '^[[:space:]]*root[[:space:]]*='
containerd config dump | grep -qE '^[[:space:]]*root[[:space:]]*=[[:space:]]*"/<новый-путь>/containerd"' \
  && echo "GATE OK: эффективный root изменён" \
  || { echo "GATE FAIL: эффективный root НЕ изменён — СТОП, шаг 4 (mv) НЕ выполнять"; sudo cp -a /etc/containerd/config.toml.bak-$(date +%F) /etc/containerd/config.toml; }
# Если напечатан GATE FAIL — НЕ выполняйте шаг 4 (mv каталога) и шаг 5 (запуск демонов):
# разберитесь с форматом и источником значения вручную (drop-in, иное форматирование, include).
# 4) Переименовать старый каталог (точка отката, НЕ удалять).
sudo mv /var/lib/containerd /var/lib/containerd.old-$(date +%F)
# 5) Запустить containerd, затем docker.
sudo systemctl start containerd
sudo systemctl start docker
containerd config dump | grep -E '^[[:space:]]*root'
docker info | grep -i -E "storage driver|containerd"
# 6) ГЕЙТ: образы и тома видны, состояние совпадает с "до" (по выводам 1.4/1.5).
docker images; docker system df -v; docker volume ls
# СТОП-УСЛОВИЕ: если `docker images` пуст, или в `docker volume ls` нет тома с pgdata, или
# `docker info -f '{{.DriverStatus}}'` не содержит io.containerd.snapshotter.v1 — НЕ запускать
# `docker compose up`: сначала ОТКАТ (ниже). Compose на пустом store создаст пустой том pgdata.
docker compose -f docker-compose.yml ps
# 7) Старый каталог удалять только после успешной проверки и отдельным решением, позже.
# ОТКАТ: остановить docker и containerd, вернуть root в config.toml, вернуть каталог:
#   sudo systemctl stop docker.socket docker; sudo systemctl stop containerd
#   sudo mv /var/lib/containerd.old-<дата> /var/lib/containerd
#   восстановить config.toml из .bak; sudo systemctl start containerd docker
# Что теряется при ошибке: docker создаст ПУСТОЙ store в новом месте — образы «исчезнут» (физически
# останутся в /var/lib/containerd.old-*), контейнеры не поднимутся. Данные томов (pgdata) при этом
# не теряются, если их Mountpoint не был внутри перенесённого дерева (проверьте: docker volume inspect).
```

### 4.6. Вариант D: отдельный диск/раздел вместо переноса

```bash
# [ЧТЕНИЕ] Список дисков и их размеров.
lsblk -o NAME,SIZE,FSTYPE,MOUNTPOINT,TYPE
# [⚠️ ДЕСТРУКТИВНО] Дальнейшее — форматирование нового носителя. ДЕЛАЙТЕ ЭТО ТОЛЬКО ЕСЛИ НА НЁМ НЕТ ДАННЫХ,
# и только убедившись по lsblk/parted, что выбрано именно новое устройство (ошибка в имени устройства
# уничтожает данные другого диска безвозвратно).
sudo mkfs.ext4 /dev/<новый-раздел>      # альтернатива: mkfs.xfs
# Далее — монтирование. ВАЖНО: монтировать поверх /var/lib/containerd можно ТОЛЬКО при остановленных
# docker и containerd (иначе будет монтаж поверх активного каталога).
sudo mkdir -p /mnt/containerd-store
# Смонтируйте новый раздел и перенесите в него данные по процедуре 4.5 — либо сразу монтируйте его
# в /var/lib/containerd, но только когда оба демона остановлены и вы готовы к переносу данных.
# Для постоянства добавьте в /etc/fstab запись с UUID (получить: sudo blkid /dev/<новый-раздел>),
# затем проверьте: sudo mount -a && findmnt /var/lib/containerd
# ВНИМАНИЕ: если смонтировать пустой раздел поверх непустого каталога, старые данные не удаляются,
# но становятся невидимыми; docker создаст новый store. Проверяйте df и содержимое после монтирования.
```

### 4.7. Общий порядок действий при «физически мало места»

1. Доказать, что дело в объёме, а не в мусоре/чужих данных (разделы 1 и 3).
2. Если есть свободные экстенты в VG — расширить LV/ФС (4.3, наименьший риск).
3. Если нет — перенести store (4.4/4.5) или подключить новый диск (4.6). В обоих случаях: окно простоя, дамп БД, снапшот, переименование старого каталога вместо удаления.
4. Убедиться, что `docker images`, `docker volume ls`, `docker ps -a` совпадают с состоянием «до».
5. Возобновить сборку по разделу 5.

## 5. Шаг 5. Дисциплина сборки при нехватке места

Порядок жёсткий: **сначала освободить место и проверить запас — потом собирать.** Сборка на почти полном диске — это 1302 секунды работы и ENOSPC в самом конце, как в исходном инциденте.

```bash
# [ЧТЕНИЕ] Гейт перед сборкой: место и inode должны быть в норме (см. 4.1).
cd <каталог-деплоя>
df -h /var/lib/containerd; df -i /var/lib/containerd
docker system df
# Ожидаемо: свободно ≥ 10 GB на нужной ФС и Use%/IUse% далеки от 100%.
# Если гейт не пройден — НЕ НАЧИНАТЬ сборку, вернуться к разделу 3 или 4.
```

```bash
# [БЕЗОПАСНО ДЛЯ ДАННЫХ] Ручная «предсборочная» обрезка кэша: оставить 2 GB.
docker builder prune --force --keep-storage 2GB
# Ожидаемо: небольшой объём освобождён. Кэш сборки не является данными, потеря не критична.
```

```bash
# [БЕЗОПАСНО] Разделить скачивание и сборку: сначала базовые образы, потом сборка.
docker pull python:3.12-slim
docker pull postgres:16-alpine
docker pull nginx:alpine
# Ожидаемо: "Status: Downloaded newer image" или "Image is up to date".
# Смысл: если ENOSPC случится на pull — это видно сразу и на понятном шаге, а не «внутри» сборки.
# Здесь же ловится гипотеза H3 (перетегированный базовый образ): заодно проверьте metadata (2.3-D).
```

```bash
# [БЕЗОПАСНО, но создаёт слои] Собирать ПО ОДНОМУ сервису, последовательно: app, затем chainlit.
DOCKER_BUILDKIT=1 docker compose build app
docker compose up -d db
docker compose up -d app
df -h /var/lib/containerd; df -i /var/lib/containerd
DOCKER_BUILDKIT=1 docker compose build chainlit
docker compose up -d chainlit web
docker compose ps
# Ожидаемо: каждый build завершается успешно; df после каждого шага показывает запас.
# `docker compose up --build` заменён на build+up намеренно: он не пересобирает оба сервиса параллельно
# и не оставляет «висеть» всю работу до момента, когда место уже кончилось.
# DOCKER_BUILDKIT=1 — в 24.x режим и так по умолчанию; явное указание фиксирует поведение.
```

```bash
# [БЕЗОПАСНО] Если нужно ограничить параллелизм сборки compose (собирать строго по одному).
COMPOSE_PARALLEL_LIMIT=1 docker compose build
# Ожидаемо: сервисы собираются по одному. Полезно на диске «в обрез» и на медленном CPU.
```

Чего избегать при нехватке места:

| Приём | Почему плохо |
|---|---|
| `docker compose build --no-cache` / `docker build --no-cache` | Отключает переиспользование кэша: все слои пересобираются и заново занимают место. Пиковое потребление вырастает кратно. На почти полном диске — гарантированный ENOSPC. |
| Параллельная сборка двух сервисов на полном диске | Пики потребления складываются. Итог — тот же ENOSPC, но труднее понять, какой сервис его вызвал. |
| Сборка «на удачу» без проверки `df`/`df -i` | Тратит 20+ минут и оставляет недописанные снапшоты, которые сами занимают место. |
| Удаление того, что «вроде не нужно», вместо 3.5/3.6 | Удаление каталогов store вручную ломает containerd (см. раздел 7). |

Полезные (необязательные) меры на будущее, вне этого ранбука:

* `RUN --mount=type=cache,target=/root/.cache/pip` в Dockerfile вместо «голого» `pip install` — ускоряет сборки, но **увеличивает** build cache (чистится через 3.2). Наш текущий `pip install --no-cache-dir` слои не раздувает.
* `.dockerignore` в контекстах сборки (`backend/`, `chainlit/`) — уменьшает контекст и, соответственно, размер слоёв.
* Периодическая (по расписанию) обрезка кэша: `docker builder prune --filter "until=168h"` — предотвращает «накопление до ENOSPC».

## 7. Чего НЕ делать

* **Не выполнять `docker volume prune --all` (и `docker volume prune -a`) на проде.** По документации Docker 24.x `--all` удаляет и **именованные** неиспользуемые тома, включая `netops-llm_pgdata` → потеря базы PostgreSQL. См. 3.7.
* **Не выполнять `docker compose down -v`** на проде: `-v` удаляет тома. Допустимо только `docker compose down` без `-v`, и только вне окна работы сервиса.
* **Не выполнять `docker system prune -a --volumes` (и `docker system prune --volumes`) на проде.** Флаг документирован как «anonymous volumes», но примеры в официальной доке v24.0.6 показывают удаление именованного тома, т. е. поведение неоднозначно → команда запрещена консервативно. См. 3.7.
* **Не удалять `docker volume rm` без свежего, выгруженного наружу дампа БД** и без поштучного разбора: `docker volume inspect <NAME>` + `docker ps -a --filter volume=<NAME>`.
* **Не удалять каталоги store вручную** (`rm -rf /var/lib/containerd/...`, `/var/lib/docker/overlay2`, `.../snapshots/<N>`). Это ломает учёт containerd/docker: появляются ошибки `snapshot does not exist`, образы «пропадают» необратимо. Для очистки использовать только штатные команды (`docker builder prune`, `docker image prune`, `docker container prune`).
* **Не удалять недописанный снапшот `<N>` из сообщения об ошибке вручную.** Он либо будет собран мусорщиком после перезапуска (3.6), либо удалится вместе с образом штатной командой.
* **Не использовать `--no-cache` как «лечение»** ENOSPC: это увеличивает потребление и время (раздел 5).
* **Не «освобождать место» удалением данных БД**, остановкой только контейнера `db` (место не освободится, а сервис ляжет) или удалением `/var/lib/postgresql` — данные не восстанавливаются.
* **Не обрезать активные лог-файлы через `truncate`/`rm`** в надежде «вернуть место»: для journald есть `journalctl --vacuum-size`, для остального — сначала понять, кто пишет (1.6). Удаление открытого лога не освобождает место до перезапуска писателя.
* **Не запускать `docker image prune -a` перед сборкой, не убедившись, что базовые образы доступны в реестре/зеркале.** Иначе сборка упрётся в сеть/доступность, а не в диск.
* **Не менять `/etc/docker/daemon.json` и `/etc/containerd/config.toml` без бэкапа файла и без остановки служб в правильном порядке** (сначала docker, потом containerd — при остановке; при запуске — containerd, потом docker).
* **Не игнорировать `df -i`.** «Свободные гигабайты» при исчерпанных inode не помогают, а текст ошибки тот же.
* **Не делать `reboot` первой реакцией.** Перезагрузка не освобождает место и рискует не поднять БД, если диск заполнен. Сначала раздел 1.
* **Не выкладывать в тикеты/чат содержимое `.env`, дампов БД и журналов контейнеров** — там могут быть значения секретов и внутренние адреса.
* **Не считать этот ранбук «выполненным».** Ни одна из команд здесь не запускалась на `<прод-хосте>` (см. шапку и раздел 10).

## 8. Быстрый чек-лист оператора (copy-paste порядок)

1. `WORK="$HOME/enospc-$(date +%F)"; mkdir -p "$WORK"; echo "$WORK"` — каталог протокола (1.0).
2. `df -h; df -i` — блоки и **inode** (1.1).
3. `df -h /var/lib/containerd; df -i /var/lib/containerd` — прицельно по ФС из ошибки (1.1).
4. `findmnt -T /var/lib/containerd -o TARGET,SOURCE,FSTYPE,SIZE,USED,AVAIL,USE%; lsblk -f; sudo vgs` — раздел/LV/ФС (1.2–1.3).
5. `docker info --format 'RootDir={{.DockerRootDir}} Driver={{.Driver}}'; docker system df -v` — что и где занимает (1.4).
6. `sudo du -xh --max-depth=1 /var/lib/containerd 2>/dev/null | sort -h | tail -20` — что раздулось (1.5).
7. `docker volume ls | grep -i pgdata; docker volume inspect netops-llm_pgdata` — где данные БД (3.0).
8. `docker compose exec -T db pg_dump -U netops -Fc netops > "$WORK/netops-backup-$(date +%F).dump"` + `scp` наружу — **бэкап обязателен** (3.0). Если `docker` требует `sudo` (оператор не в группе `docker`), перенаправление всё равно должно выполняться вашим shell: `sudo sh -c 'docker compose exec -T db pg_dump -U netops -Fc netops' > "$WORK/netops-backup-$(date +%F).dump"` (подробнее — 3.0, блок с дампом).
9. `docker builder prune --force --keep-storage 5GB` → при необходимости `docker builder prune --force` — безопасное освобождение (3.2).
10. `docker image prune --force` — только dangling (3.3).
11. `df -h; df -i` — проверка. Достаточно? → перейти к сборке (раздел 5). Нет → следующий шаг.
12. `docker image prune --all --force --filter "until=168h"` — с проверкой доступности реестра (3.4).
13. `docker rmi <IMAGE_ID>` — точечно, по крупнейшим неиспользуемым (3.5).
14. `sudo systemctl restart docker` — мягкий вариант; если `df` не изменился — вариант 2 из 3.6 (`containerd`, затрагивает все контейнеры хоста). Проверить `df`.
15. Если места объективно мало — раздел 4 (расширение LV → перенос store; том `netops-llm_pgdata` не удалять).
16. Сборка: `DOCKER_BUILDKIT=1 docker compose build app` → `up -d db app` → `DOCKER_BUILDKIT=1 docker compose build chainlit` → `up -d chainlit web` → `docker compose ps` (раздел 5).
17. Если снова ошибка с `python3.11` — раздел 2 (чужой слой, другой checkout, перетегированный базовый образ).

## 9. Проверка флагов и версий (что подтверждено документацией)

Все используемые в документе команды и флаги существуют в Docker CLI 24.x. Ниже — сверка с официальной документацией/мануалами и способ проверить наличие флага на конкретном хосте (штатный `--help` — самый надёжный источник для вашей сборки CLI).

| Команда/флаг | Статус | Проверка на хосте |
|---|---|---|
| `df -h`, `df -i`, `du -xsh`, `du -xh --max-depth=1`, `findmnt -T -o`, `lsblk -f`, `stat -f`, `vgs/lvs/pvs`, `losetup -a`, `lsof +L1`, `journalctl --vacuum-size` | Стандартные утилиты Linux (coreutils/util-linux/LVM/lsof/systemd) | `du --version`, `findmnt --version`, `journalctl --version` |
| `docker system df -v` | Есть (`--verbose` — подробная разбивка) | `docker system df --help` |
| `docker builder prune -a/--all`, `--filter "until=…"`, `--force`, `--keep-storage` | Есть | `docker builder prune --help` |
| `docker buildx prune --min-free-space` / `--max-used-space` / `--reserved-space` | Есть в свежих buildx; в базовом CLI 24.x может отсутствовать → в ранбуке не используются как обязательные | `docker buildx prune --help` |
| `docker buildx du` | **ОПЦИОНАЛЬНО**: команда плагина buildx; если `docker buildx` не установлен/старый — пропустить | `docker buildx version && docker buildx du --help` |
| `docker image prune -a/--all`, `--filter "until=…"`, `--force` | Есть | `docker image prune --help` |

| `docker volume prune -a/--all`, `--filter` (**поддерживается только `label=…`**), `--force` | Есть; `--all` расширяет удаление на именованные неиспользуемые тома — **опасно для `pgdata`**, поэтому в ранбуке команда запрещена (3.7) | `docker volume prune --help` |
| `docker system prune --all`, `--volumes`, `--force` | Существует; `--volumes` описан как «Prune anonymous volumes», но здесь команда **запрещена** консервативно (3.7) | `docker system prune --help` |
