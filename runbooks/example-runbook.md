# Пример: проверка доступности сервиса мониторинга (вымышленный runbook)

> Этот документ — **учебный образец для dev-стенда и проверки RAG-поиска**.
> Все имена, адреса и значения вымышлены. На проде заменяется реальными
> runbook'ами (файл можно удалить). Секретов здесь нет и быть не должно.

## Когда применять

Сервис мониторинга (далее «монитор») не отвечает на страницу статуса, либо
агент сообщает, что данные по инфраструктуре недоступны. Сначала убедитесь,
что недоступность не плановая: загляните в календарь работ.

## Проверка

1. Проверить, что процесс запущен на хосте монитора
   (пример для тестового адреса из диапазона RFC 5737 — `192.0.2.10`).
2. Проверить ответ API: `GET /api/status` должен вернуть JSON со статусом
   `ok` и ненулевым счётчиком опрашиваемых устройств.
3. Проверить свободное место на разделе с базой монитора: при заполнении
   выше 90 % опрос останавливается, в логах появляются ошибки записи.
4. Если API отвечает, а данные в агенте устарели — проверить время последнего
   успешного опроса (поле `last_poll_at`) и часовой пояс сервера.

## Что делать

| Симптом | Действие |
|---|---|
| процесс не запущен | запустить сервис штатным способом, проверить статус через 2 минуты |
| диск заполнен > 90 % | освободить место по процедуре обслуживания, не удалять базу монитора |
| API отвечает, данных нет | проверить учётную запись опроса в менеджере секретов (значение в документе не приводится) и сетевую доступность опрашиваемой подсети |

## Откат

Если после перезапуска данные не появились за 15 минут — вернуть предыдущую
конфигурацию сервиса из системы контроля версий и сообщить ответственному
за мониторинг. Данные монитора не удалять: они нужны для разбора.

# Пример: ротация журналов сервиса (вымышленный runbook)

## Когда применять

Раздел с журналами сервиса заполнен более чем на 80 %, либо в журнале
появились записи об ошибках записи. Ротация — плановая операция, выполняется
в окно обслуживания.

## Порядок

1. Убедиться, что свободного места на разделе достаточно для копии текущего
   журнала (не менее двух размеров файла).
2. Остановить сервис, который пишет журнал, штатной командой.
3. Переименовать текущий файл журнала с датой в имени (формат `YYYY-MM-DD`).
4. Запустить сервис и убедиться, что новый файл журнала создаётся и в него
   идут записи.
5. Удалить архивные журналы старше срока хранения, установленного регламентом
   (не удаляйте журналы за последние 30 дней — они нужны для разбора инцидентов).

## Проверка

* сервис в статусе «работает», новые записи появляются;
* в журнале нет ошибок записи;
* свободного места на разделе больше 30 %.

## Откат

Вернуть исходное имя файла журнала и перезапустить сервис. Если сервис
не стартует — проверить права на каталог журналов.

# Пример: подготовка отчёта по инциденту (вымышленный runbook)

## Когда применять

После устранения инцидента, повлиявшего на доступность сервиса, в течение
одного рабочего дня.

## Что включить в отчёт

1. Время начала и обнаружения инцидента, время восстановления.
2. Затронутые сервисы и пользователей (без персональных данных).
3. Причина: техническая и организационная (почему не заметили раньше).
4. Что сделали для восстановления — по шагам, с временами.
5. Меры, чтобы не повторилось, с ответственными и сроками.
6. Ссылки на журналы и заявки (сами журналы к отчёту не прикладываются).

## Проверка

Отчёт согласован с ответственным за сервис, меры внесены в трекер задач,
для повторяющейся причины обновлён соответствующий runbook в этом каталоге.

## Откат

Не применимо: документ не меняет инфраструктуру. Если причина не установлена —
отчёт переводится в статус «расследование продолжается» с датой следующего
разбора.
